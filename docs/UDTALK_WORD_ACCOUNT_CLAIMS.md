# 単語登録アカウント所持申請

## 利用方法

- 公開フォーム：`/udtalk/word-account-claim`。ログインや他ページ経由のアクセスは不要です。
- 管理一覧：`/admin/udtalk-word-account-claims`。管理者トップから開けます。既存の管理者セッションを使います。
- アカウント名、画像1枚、登録単語と読み3組、設定希望メールアドレスと確認入力がすべて必須です。同一の単語・読みの組の重複は受け付けません。
- 画像はPNG・JPEG・WebPの5MB以下です。サーバーでも容量、ファイルの先頭バイト、申告された形式を確認します。HEIC・SVG・PDFは対象外です。
- 日本語を標準表示とし、`?lang=en`で英語表示に切り替えられます。
- 送信後は受付番号を表示し、設定希望メールアドレスへ日本語の受付メールを1通送ります。「確認に2〜3日ほどお時間をいただきます。あらかじめご了承ください」と案内します。元の単語登録サーバーのアカウント更新は行いません。

## 環境設定

既存の`FIREBASE_ADMIN_CREDENTIALS`と`SESSION_SECRET`を使用します。サービスアカウント用の環境変数を増やす必要はありません。

| 環境変数 | 内容 |
| --- | --- |
| `UDTALK_STORAGE_BUCKET` | 必須。Cloud Storageのバケット名。`gs://`を付けず、Firebaseコンソールに表示される名前を指定します。 |
| `UDTALK_FIRESTORE_ENV` | 任意。未設定時は`production`。検証環境では`staging`などに分離します。英数字・ハイフン・アンダースコアのみ使用できます。 |
| `SENDGRID_API_KEY` | 受付メール用。既存の一斉メール送信と同じAPIキーを使用します。 |
| `SENDGRID_FROM_EMAIL` | 受付メールの送り元。通常の一斉メール送信と同じアドレスを使用し、差出人名は「UDトーク」です。 |

画像保存にはCloud Storageバケットの作成と、既存サービスアカウントへのオブジェクト読み書き権限が必要です。バケットは非公開で運用してください。FirestoreとStorageの`UDTalk`配下に対するクライアントSDKからの読み書きを許可しないでください。既存の全パス許可ルールがある場合、個別の拒否ルール追加だけでは保護できないため、その許可範囲も見直してください。アプリはAdmin SDK経由で読み書きします。

Storageの設定は[Firebase公式ドキュメント](https://firebase.google.com/docs/storage/admin/start)を参照してください。

## 保存先と閲覧

- Firestore：`UDTalk/{environment}/wordAccountClaims/{受付番号}`。
- Storage：`UDTalk/{environment}/wordAccountClaims/{受付番号}/screenshot`。
- アカウント名、メールアドレス、単語と読み、サーバー受付日時、画像の保存先・形式・サイズ、再送照合用ハッシュを保存します。確認入力のメールアドレスと元の画像ファイル名は保存しません。
- 既存の`Mojidas`配下の申請・アカウント情報は変更しません。共通のWebセッション保存先は従来の設定を継続します。
- 公開URLやダウンロードトークンは発行しません。画像は管理者セッションを確認するExpressルートから配信します。一覧・画像・フォームはキャッシュ禁止・検索インデックス対象外です。
- 一覧は新しい申請から20件ずつ取得し、「次の20件」で過去分を閲覧できます。各行には申請日時・アカウント名・メールアドレス・詳細ボタンを表示します。登録単語と読み3組、画像、受付番号は詳細モーダルにまとめています。画像は詳細を開いた際に取得し、別タブで確認するリンクも用意しています。追加の複合インデックスは不要です。

## 送信と障害時の動作

- 受付メールは申請と画像の保存成功後に送ります。宛先は申請されたメールアドレスだけとし、単語と画像はメールに含めません。本文にはアカウント名・受付番号と、確認に2〜3日ほどかかることを記載します。通常の一斉メールの控え送信機能とは別に、送り元への控えは追加しません。
- `receiptEmail`に送信待ち・送信中・送信受付済み・失敗・結果不明を保存し、管理画面の詳細モーダルに表示します。送信受付済みはSendGridが受け付けた状態であり、受信者への配達完了を意味しません。
- Firestoreトランザクションで送信権を取得し、同一フォームの再送・並行処理・再起動で重複送信しません。送信開始前の中断は同じフォームの再送で回復します。送信開始後の中断・通信結果不明・受付後の記録失敗は自動再送せず、SendGridの受付記録と照合して確認してください。失敗しても申請データと受付結果は保持します。
- 本機能導入前の申請には遡及送信しません。`MOJIDAS_BROADCAST_FROM_EMAIL`は使用せず、既存の`SENDGRID_FROM_EMAIL`を使用します。メール設定の詳細は[管理ログイン仕様](ADMIN_AUTH.md)を参照してください。

- フォームの署名をセッションに結び付け、CSRFと申請IDの改ざんを防ぎます。JavaScriptが無効でも必須項目・メール一致をサーバーで検証します。
- 同一フォーム・同一内容の再送は1件の申請になります。送信済みの内容を変えて再送すると拒否します。別の申請にはフォームを開き直します。
- Storageの作成条件とFirestoreトランザクションで並行送信時の上書きを防ぎます。
- 画像保存後にFirestoreへの書き込みが失敗した場合、画像を残して同一フォーム・同一内容の再送で回復します。結果不明な書き込み後の画像削除で成功済みの申請を壊さないためです。再送されなかった画像は残ります。必要に応じて申請ドキュメントが存在しない十分古い画像を運用側で確認・削除してください。自動削除は行いません。
- 送信は接続元IPごとに15分間10回までです。制限はプロセス内で管理します。複数インスタンス全体の制限が必要な場合はプロキシ側で設定してください。
- 入力エラー時は入力テキストを保持し、画像の再選択を案内します。保存失敗時は成功画面を表示しません。

## 検証

`npm run test:udtalk-claims`で入力検証、画像制限、再送・並行送信、障害からの再送回復、ページング、管理者認証、CSRF、画像保護、HTMLエスケープに加え、受付メールの送り元・宛先・本文・重複抑止・送信と記録の障害を検証します。Firestore・Storage・SendGridは隔離したfixtureで代替し、実データへの書き込みや実メール送信は行いません。

実環境では非公開の検証用バケットとFirestore環境を用意し、`npm start`後にフォームから1件送信して管理一覧と画像を確認してください。
