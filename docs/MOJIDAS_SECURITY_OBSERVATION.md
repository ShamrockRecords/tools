# アカウントを維持した利用制限と監査

不審なアカウントの登録・ログインを維持したまま、対象者による新しい認識・翻訳・購入を拒否し、操作を記録する。Firebaseユーザーの無効化、トークン失効、残高の没収、データ削除は行わない。サーバー共通の制限なので、Mac・Windows・API直接呼び出しに同じ判定を適用する。

## 設定

サーバー起動時に以下を読み込む。空欄の場合は対象なし。不正な設定は起動時にエラーとし、黙って制限を外さない。

| 環境変数 | 用途 |
| --- | --- |
| `MOJIDAS_RESTRICTED_USER_IDS` | 費用操作を制限するFirebase UID。カンマ区切り、大小文字を区別 |
| `MOJIDAS_RESTRICTED_EMAIL_DOMAINS` | 費用操作を制限するメールドメイン。カンマ区切り、大小文字を無視した完全一致 |
| `MOJIDAS_SECURITY_WATCH_IPS` | 監査のみ行う接続元IP。カンマ区切り。IPだけでは利用を拒否しない |

UIDとドメインはどちらかが一致すれば制限する。UID指定は同じアカウントのメール変更後も有効。ドメイン指定は同じドメインで後から作成されたアカウントにも有効。別ドメイン・別UIDへの移動を防ぐものではない。

設定変更後はサーバーを再起動する。今回のソース変更だけでは本番設定・デプロイを行わない。認識キー設定の変更・失効も別途実施する。

## 利用制限

Firebaseで検証した現在のUserRecordのUID・メールで判定し、要求本文・自己申告ヘッダーは利用しない。通常ユーザーや法人・招待ユーザーでも、指定対象なら同じ制限を受ける。

対象者の以下の操作は、外部サービスや予約・ジョブ作成の前に `403 / USAGE_RESTRICTED` を返す。

- `POST /api/mojidas/usage/reservations`
- `POST /api/mojidas/acp/instant-appkey`
- `POST /api/mojidas/translation/realtime`
- `POST /api/mojidas/translation/formal`
- `POST /api/mojidas/billing/checkout-session`

登録、メール確認、ログイン、更新、残高確認、単語同期、本人によるアカウント削除は既存の認証条件で利用できる。既存の予約のheartbeat・完了・取消と既存翻訳結果の取得も維持し、未精算の予約を残さない。正式翻訳の見積もりと対応言語一覧は制限対象外。制限された操作のエラーはアプリにも表示されるため、監視の事実を必ず隠せる仕組みではない。

Stripeで作成済みの決済や実行中の翻訳ジョブは取り消さない。Webhookによる支払済み時間の付与も継続する。これらを止める場合は、既存データ・決済への影響を確認して別途対応する。

## 監査記録

対象UID・ドメインのMojidas API操作と、監査対象IPから共通サーバーへ来る操作を記録する。認証失敗時は対象ドメインの自己申告を区別して記録し、検証済みUIDとして扱わない。一般ユーザーを新たに全件追跡する変更ではない。

保存先は `Mojidas/{environment}/securityEvents/{eventID}`。日時、検証済みUID（判明時）、識別根拠、メールドメイン、接続元IP、ホスト、HTTPメソッド、ルートテンプレート、パスのSHA-256、応答コード、エラーコード、所要時間、中断有無、User-Agent（最大200文字）を保存する。IPはExpressの`req.ip`を使い、転送ヘッダーの先頭を直接信用しない。IP・User-Agentだけで操作者を断定しない。

パスワード、認証コード、トークン、Cookie、要求・応答の本文、音声、翻訳文、URLクエリは保存しない。動的なパスの値も平文では保存せず、ルートテンプレートとパスのハッシュで照合する。User-Agentは利用者の自己申告である。

同じイベントを構造化サーバーログにも出す。監査DBの障害でログインを失敗させず、利用制限も解除しない。DB障害時は秘密情報を含まない警告を出し、サーバーログに残す。応答後の非同期保存なので、プロセス強制終了時などの完全な記録保証はない。

監査による追加負荷を抑えるため、1プロセス毎分120件・同時未完了書込20件まで。超過時はその分のイベントを省略し、同じ分に警告を1回出す。全通信を漏れなく記録する仕組みではなく、複数プロセスでは上限もプロセス数分になる。

`expiresAt`に30日後を設定する。**実際の自動削除にはFirestoreの`securityEvents.expiresAt`にTTL設定が必要**。このソース変更ではTTL設定を適用しない。TTL未設定なら30日後も物理的には残る。クライアントへ当コレクションの読取権限を与えない。Herokuの標準履歴は直近1,500行のみなので、永続保存失敗時の過去追跡には限界がある（[公式説明](https://devcenter.heroku.com/articles/limits)）。

## 既存の長期キーについて

この制限は新たなキー取得を止めるもので、取得済みのACP長期キーを失効させない。キーを保有した利用者のACP直接通信はMojidasを通らず、Mojidasの利用台帳・監査だけでは実利用量を確定できない。

ACP側の利用記録・既存キーの扱いを確認する必要がある。短期キーへの移行や中継方式への変更は認識動作に関わる別作業。特にファイル認識は処理待ち・再開時にも有効なキーが必要なため、有効期限だけを短くしない（[AmiVoice公式説明](https://docs.amivoice.com/amivoice-api/manual/api-key-additional-features)）。

## 検証

`npm run test:mojidas-security` は隔離Firestoreと置換した外部サービスで、対象者のログイン維持、UID・ドメイン判定、直接APIへの制限、通常ユーザーの操作、拒否・再送時のデータ不変、既存予約の精算、監査障害・中断・記録上限、機密情報除外を検証する。本番アカウント・キー・音声認識・メール・決済は使わない。

2026-10-26、Mac上のNode.js 24.22.1で新規テストと`npm test`全体が成功した。Mac・Windowsアプリのビルド／実アプリ操作、本番へのデプロイ、監査コレクションのTTL設定は未実施。アプリのソース変更はなく、共通APIに適用する変更である。以下の実アプリ確認はサーバーの自動テストとは別に必要。

本番反映後はMacとWindowsそれぞれで、隔離した確認用アカウントを用いて以下を確認する。Macでの結果をWindowsの確認に代用しない。

1. 対象ユーザーでもログインと残高確認ができる。
2. ライブ／ファイル認識、リアルタイム／正式翻訳、購入開始で利用制限の案内が出て、外部認識・翻訳・決済や新しい予約が始まらない。
3. 通常ユーザーは認識・翻訳・購入開始が従来どおり利用できる。確認用動画の映像・音声、停止／再開、シーク、閲覧／編集、セッション切替・再オープンを確認する。
4. 制限前に作った確認用予約を終了しても、残高・履歴が壊れず重複精算されない。
5. 対象ユーザーの操作が`securityEvents`に保存され、機密情報が含まれない。

本番の不審アカウントでテスト操作・ログインを行わず、調査記録を汚さない。
