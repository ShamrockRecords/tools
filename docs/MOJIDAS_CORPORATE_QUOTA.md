# 法人利用上限の運用・配布確認

## 配布前に必要な設定

- `firestore.indexes.json`に記載した`corporateUsageLedger`の複合インデックス（`domain ASC`, `occurredAt ASC`、collection scope）を対象Firebaseプロジェクトへ追加し、作成完了を待つ。既存の別機能のインデックスは削除しない。このファイルは今回の追加分だけであり、本番の全インデックス一覧ではない。
- メールは既存SendGridを使う。`SENDGRID_API_KEY`と、`MOJIDAS_AUTH_FROM_EMAIL`または`SENDGRID_FROM_EMAIL`を設定する。新たな定期ジョブは不要。
- サーバーを全インスタンス更新する。Mac／Windowsとも新エラーで認識を停止する版を配布してから、停止設定を有効にする。旧アプリも新規開始は拒否されるが、進行中の新エラーによる停止は保証できない。
- この変更ではデプロイ、インデックス作成、本番メール送信、本番データ変更を自動実行しない。

## データ

プラン変更時の上限初期値は従量制0時間・ライト50時間・スタンダード100時間・カスタム空欄（上限なし）。選択時に入力値を上書きし、サーバーもプラン変更時に同じ値を適用する。トライアルは入力した有効期間内の上限時間を使う。従量制の0時間は全利用が超過分になることを表す。停止・通知設定は独立しているため、上限到達時停止が有効なら0時間で利用停止となる。

プラン・上限・期間などの設定変更時にキャッシュ世代を更新し、保存後は利用台帳から再集計する。トライアルからライト等へ切り替えた場合は、トライアル中も含む当月の実利用時間を月間上限から差し引く。ライトとスタンダードの往復でも古いキャッシュを使わず超過を再計算する。利用台帳、過去月、個人残高は変更しない。月別実績は引き続き暦月単位。期間外に受信した精算は台帳に残すが、トライアル期間内の集計には含めない。

販売店ポータル・管理画面には年別の月次一覧も表示する。1月から12月までの暦月集計（`corporateUsageMonths`）を読み、未利用月は0、末尾に年間合計を表示する。前年・翌年ボタンは既存のDOM更新で切り替え、詳細設定などのPOST後も選択年を保持する。上限判定と同じ日本時間の暦月による実績表示。追加readは閲覧可能なドメインごとに12 document／表示。データへのwriteはない。

`corporateDomains`に`limitMilliseconds`（nullは無制限）、`resetDay`、`stopAtLimit`、`notifyAtOneHour`、`quotaRevision`を保存する。設定変更で台帳や個人残高を削除しない。トライアルは有効期間全体を集計し、月ごとのリセットは行わない。新規設定時は有効期間を必須とする。期間未設定の旧トライアルは初回承認日から累計し、次のプラン保存時に期間を設定する。それ以外のプランのリセットは日本時間の毎月1日0時に固定する。旧`resetDay`や`approvedAt`の日付は集計境界に使用しない。新規保存の`resetDay`は1。月途中の開始でも上限は日割りせず満額付与し、翌月1日に再び満額となる。再承認で初回承認日を書き換えない。

`corporateQuotaPeriods`は利用台帳から再構築可能な期間別集計キャッシュ。初回には対象ドメイン・暦月だけ台帳を読む。毎月1日固定への移行時は`monthly_`を付けた別キャッシュキーを使用し、旧集計を流用せず台帳から再構築する。旧台帳・キャッシュは削除しない。以後は利用確定transactionで一緒に更新する。既存の暦月集計も維持する。`corporateQuotaNotifications`は期間と宛先のハッシュ別に送信済み状態と送信リースを保存する。

通常の利用確定では従来に加えてドメイン設定と期間キャッシュ各1 read、キャッシュ1 write。期間初回は対象期間の台帳件数分のreadが追加される。通知対象時は販売店1 readと宛先別の送信状態のread/writeが加わる。待機中の定期通信は増やさない。

## 受け入れ確認

1. 販売店ポータルでプランを開き、上限、停止・通知を保存する。画面全体をリロードせず反映する。他店ドメインの変更は拒否する。
2. テストドメインで上限直前から認識し、同時利用・再送を含め、個人残高を消費せず上限到達で停止する。停止をオフにした場合は継続し、超過欄が増える。
3. 上限を増減・解除しても台帳を保持する。月途中の開始で満額の上限、日本時間の月末最終時刻と翌月1日0時、閏年、旧リセット日からの再集計を確認する。
4. 残り1時間で組織と販売店へ届くこと、同じ宛先なら1通、報告再送でも重複しないこと、送信失敗時に次の報告で再試行することを確認する。配送遅延があり、メールとDBの間の障害では厳密なexactly-onceは保証しない。
5. 上限は確定利用量による判定。ファイル・翻訳の完了時計上や並行利用・報告間隔分は超過しうる。予約による厳密な事前消費制限ではない。

自動試験は`npm run test:partners`。隔離DB・ローカルHTTPの検証であり、本番Firestore・実メール配送・ブラウザ外観・アプリ実機の確認とは別。
